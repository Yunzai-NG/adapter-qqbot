## 修复：群聊 @机器人 后指令匹配不到

- 现象：群里发 `@机器人 #消息测试`，日志只出现 `命令命中 relay-checkin:^[\s\S]+$`，
  message-test 的 `#消息测试` 不响应。
- 实测报文（logs/yunzai-2026-10-22.log）：`content = "<@5519A1A02E6BBE79C222FA4611115C66> #消息测试"`，
  即 `<@大写OPENID>`（**不带斜杠**）；客户端展示成 `<@//…/>` 只是 UI 渲染。
- 根因：`adapter-qqbot/src/codec.ts` 的 `decodeMessage` 只认 `<@!?(everyone|\d+)>`，openid 不是纯数字，
  整段留在 text 段里，`e.text` 变成 `<@5519…> #消息测试`，所有 `^#指令` 命令匹配失败，
  只剩别的插件的兜底规则能命中。
- 修法：tokenRegex 第一分支 id 放宽为 `[\w-]+`（`everyone` 仍优先），另保留
  `<@!?\/\/?([^>\s/]+)\/?>` 斜杠写法；emoji 组下标为 3。codec.test 覆盖 `<@OPENID>`、斜杠、`<@!…>`、emoji 混排。
- 验证：用真实报文跑 dist，`e.text === "#消息测试"` 且菜单正则匹配；`tsc -b`、eslint、codec/events/outbound/markdown 测试全绿。
- 遗留：群聊 `at` 段的 uid 是 openid，`selfId` 是真实 QQ 号，故 `e.atMe` 在群聊仍为 false
  （修复前 atUsers 为空，同样 false，无回归）。payload 里其实有 `mentions[].is_you`，可据此补 atMe。

## 追加：@ 机器人对齐 NapCat 的 at 段语义（不改核心）

- 用户先要求「收到 @ 消息直接去掉 id / 直接不要 `[@…]`」，后明确「不修改核心，适配器适配核心的
  at 消息格式」，并让参考 NapCat。
- NapCat 的做法（`plugins/adapter-napcat/src/codec.ts:244`）：`at` 段照常保留，`uid` 用 QQ 号、
  `name` 取 OneBot 的 `data.name`；因为 uid 与 `bot.selfId` 同属 QQ 号体系，核心 `atMe` 天然成立，
  日志 `describeMessage` 渲染成 `[@昵称]`。
- QQ Bot 的差异：正文 token 是 openid / 频道用户 id，`selfId` 是真实 QQ 号，两套 id 永不相等。
  故对齐方式为：`mentions` 里 `is_you: true` 的那条把 `uid` 换成 `selfId`，所有 `at` 段补
  `name`（报文 `mentions[].username`）。
- 结果：`[{type:"at",uid:"2854196810",name:"阿贝多"},{type:"text",text:" #消息测试"}]`，
  日志 `... 归途守候你(FF23…): [@阿贝多] #消息测试`；`e.atMe` 为 true。
- 期间试过但**已回退**的两条路，勿重走：
  1. 改核心 `describeMessage` 跳过 `uid === selfId` 的 at 段 —— 用户明确不修改核心，`git diff
     packages/core` 已为空。
  2. 适配器直接丢弃机器人自身的 at 段 —— 日志干净但 `e.atMe` 回退 false，且要额外处理残留空格。
- 教训：不要用 python 批量 `replace` 处理含 `return decodeXxx(...)` 的源码，会误删前缀；
  本次误伤 19 处已用正则恢复，改动后必须 `git diff` 复核。
- 校验：`tsc -b`、`tsc -p tsconfig.test.json`、eslint 全通过；测试 codec 20 / events 25 / outbound 13 /
  official-image-host 9 / media 9 / markdown 5 / file-server 5 / upload 5 全过（vitest 并发仍有
  EPERM 临时目录问题，需单文件跑）。dist 已重建。
